The WND / tagWND Object in ReactOS and Windows

A field-by-field, code-traced reference for the kernel-mode window object, contrasted with the documented Windows layout, including a discussion of the Win32k Type Isolation mitigation.

1. What is WND / tagWND?

Every visible (and most invisible) window on the screen — every dialog, every button, every menu, every desktop, every tooltip — is represented inside the kernel-mode window manager (win32k.sys on Windows; win32k.sys in ReactOS, source under win32ss/user/ntuser/) by a single instance of the WND structure. The Windows-internal name for this structure is tagWND; ReactOS calls it struct _WND with the typedef name WND. The pointer typedef PWND (i.e. WND *) is what application, user32, and win32k code commonly refer to as “a pWND”.

The HWND handle that user-mode applications pass to CreateWindow, SetWindowText, etc. is a numeric handle (a slot index into a global handle table); the actual data lives in the WND object on the desktop heap. The relationship is:

HWND  ──(handle table)──►  PWND  ──►  WND { head, state, style, ..., strName, ... }

The structure stores everything the window manager needs to know about that window:

  • identity and lifetime (head.h, head.cLockObj, destruction state bits);
  • ownership (head.pti – thread, head.rpdesk – desktop, head.pSelf – kernel self-pointer);
  • style, extended style, state bitmasks;
  • tree position (spwndParent, spwndChild, spwndOwner, spwndNext, spwndPrev);
  • geometry (rcWindow, rcClient);
  • window procedure (lpfnWndProc) and class pointer (pcls);
  • painting region (hrgnUpdate) and clip region (hrgnClip);
  • property list, scrollbar info, menu, name, window-extra-bytes size, last-active descendant, IME context, user data, activation context, clipboard listener chain, and so on.

It is, in short, the central data structure of the GUI subsystem.

2.9 Total size and the layout sentinel

Summing the fields above gives a total size of 0xEC = 236 bytes on x86 and roughly 0x180 bytes on x64. The size is enforced to be a pointer-multiple by the assertion in ntuser.h:1247:

C_ASSERT(sizeof(WND) % sizeof(PVOID) == 0);

Immediately after the typedef, the sentinel PWND_BOTTOM is defined (ntuser.h:769):

#define PWND_BOTTOM ((PWND)1)

This is used in Z-order operations to mean “bottom of stack”, distinct from NULL.

2.10 Specialized derivatives that embed WND

The header defines three subtypes (ntuser.h:771–792) that all begin with a full WND, so a PWND can be down-cast based on its fnid:

typedef struct _SBWND   { WND wnd; BOOL fVert; UINT wDisableFlags; SBCALC SBCalc; } SBWND;     // FNID_SCROLLBAR
typedef struct _MDIWND  { WND wnd; DWORD dwReserved; PVOID pmdi; } MDIWND;                       // MDI client
typedef struct _MENUWND { WND wnd; PPOPUPMENU ppopupmenu; } MENUWND;                              // FNID_MENU

Below ExStyle2, ReactOS appends six extra fields (the InternalPos block, four bitfields, pSBInfoex, ThreadListEntry, and DialogPointer) that have no counterpart in Windows. They are explicitly fenced off in the source (ntuser.h:747: “/* ReactOS */”).

Verdict. ReactOS's WND is a deliberate, byte-compatible re-implementation of the Windows 7-era tagWND, with two purposeful divergences in internal type choice (PROPLIST* → explicit list-head, and MENU* → HMENU/UINT_PTR), one commented-out Vista field (pTransform), and a clearly delimited ReactOS-only tail.

4. The PWND typedef and its three pointer relationships

PWND is just a pointer type alias for WND * (ntuser.h:767). When ReactOS code says “the WND points to pWnd” there are three distinct pointer relationships at play.

4.1 Self-pointer: head.pSelf (kernel address of itself)

When a WND is allocated, the head's pSelf is set to its own kernel address (win32ss/user/ntuser/object.c:72–86):

ObjHead = DesktopHeapAlloc(pDesk, Size);
RtlZeroMemory(ObjHead, Size);
ObjHead->pSelf  = ObjHead;     // self-pointer
ObjHead->rpdesk = pDesk;
ObjHead->pti    = pti;

So pWnd->head.pSelf always equals the kernel address of pWnd.

4.2 Handle ↔ pointer: the global handle table

The HWND in head.h indexes gHandleTable. Kernel-side resolution (win32ss/user/ntuser/window.c:123–141):

PWND FASTCALL UserGetWindowObject(HWND hWnd)
{
   PWND Window;
   if (!hWnd) { EngSetLastError(ERROR_INVALID_WINDOW_HANDLE); return NULL; }
   Window = (PWND)UserGetObject(gHandleTable, hWnd, TYPE_WINDOW);
   if (!Window || (Window->state & WNDS_DESTROYED))
       { EngSetLastError(ERROR_INVALID_WINDOW_HANDLE); return NULL; }
   return Window;
}

User-side resolution (win32ss/user/user32/misc/misc.c:357–369):

PWND FASTCALL ValidateHwnd(HWND hwnd)
{
    PCLIENTINFO ClientInfo = GetWin32ClientInfo();
    /* See if the window is cached */
    if (hwnd && hwnd == ClientInfo->CallbackWnd.hWnd)
        return ClientInfo->CallbackWnd.pWnd;     /* fast path */
    return ValidateHandle((HANDLE)hwnd, TYPE_WINDOW);
}

ValidateHandle looks up pEntry->ptr in the shared handle table and translates it to a user-mode address with DesktopPtrToUser (misc.c:297–301).

4.3 Per-thread cache: ClientInfo->CallbackWnd.pWnd

CALLBACKWND (ntuser.h:293–298) is a tiny 3-field cache living in the per-thread CLIENTINFO in the TEB:

typedef struct _CALLBACKWND {
    HWND hWnd;
    struct _WND *pWnd;
    PVOID pActCtx;
} CALLBACKWND, *PCALLBACKWND;

It is refilled by the kernel on every callback into user-mode in IntSetTebWndCallback (win32ss/user/ntuser/callback.c:96–118):

PWND Window = UserGetWindowObject(*hWnd);
PCLIENTINFO ClientInfo = GetWin32ClientInfo();
...
if (Window) {
    ClientInfo->CallbackWnd.hWnd   = hWndS;
    ClientInfo->CallbackWnd.pWnd   = DesktopHeapAddressToUser(Window);
    ClientInfo->CallbackWnd.pActCtx = Window->pActCtx;
}

So whenever a window proc is called, the matching pWnd is already sitting in the TEB and ValidateHwnd returns it without a syscall.

4.4 Why two virtual addresses for one object: desktop-heap double mapping

The WND lives on the desktop heap, which is mapped into both kernel and user address spaces at different virtual addresses. The fixed offset between the two views is ClientInfo->ulClientDelta. The two translation helpers are DesktopHeapAddressToUser (win32ss/user/ntuser/desktop.h:307) on the kernel side and DesktopPtrToUser (win32ss/user/user32/include/user_x.h:11–34) on the user side:

static __inline PVOID DesktopPtrToUser(PVOID Ptr)
{
    PCLIENTINFO  pci = GetWin32ClientInfo();
    PDESKTOPINFO pdi = pci->pDeskInfo;
    if ((ULONG_PTR)Ptr >= (ULONG_PTR)pdi->pvDesktopBase &&
        (ULONG_PTR)Ptr <  (ULONG_PTR)pdi->pvDesktopLimit)
    {
        return (PVOID)((ULONG_PTR)Ptr - pci->ulClientDelta);
    }
    /* slow path: cross-desktop mapping via syscall */
    return (PVOID)NtUserxGetDesktopMapping(Ptr);
}

The same WND therefore has two valid PWND values that differ by exactly ulClientDelta:

  • Kernel address — what head.pSelf stores and what UserGetWindowObject returns to kernel callers.
  • User address — kernel - ulClientDelta, what DesktopPtrToUser produces, what gets cached in ClientInfo->CallbackWnd.pWnd, and what ValidateHwnd hands back to user-mode callers.

This shared mapping is the key reason ReactOS does not need a second “user copy” object — one allocation is reachable from both sides at fixed offset.

5. Win32k Type Isolation: how Windows split tagWND

The Windows 7 layout described in section 3 was a single monolithic kernel object containing kernel pointers (spwndParent, pcls, etc.). For roughly fifteen years it was the favourite exploitation target in win32k.sys:

  • Reading the kernel pointer in any spwnd* field gave attackers a direct kernel-address leak (used to bypass KASLR).
  • Forging or partially overwriting a sibling WND turned almost any write-what-where into arbitrary R/W (CVE-2014-4113, CVE-2015-0061, MS15-061, CVE-2019-1458 “WizardOpium”, CVE-2021-1732, CVE-2022-21882, …).
  • HMValidateHandle historically returned the kernel pointer directly to user-mode, which became a one-shot KASLR break.

5.1 Timeline of mitigations

Windows versionMitigation
Windows 10 1607 (Anniversary, 2016) Kernel pointer references to the desktop heap removed from the Win32ClientInfo block in the TEB — closing one of the easiest kernel-address leaks.
Windows 10 1703 (Creators, 2017) HMValidateHandle returns user-mode (rather than kernel-mode) pointers; bytes written by SetWindowLong are no longer applied to the kernel object directly — killing a common write primitive.
Windows 10 1709 (Fall Creators, 2017) Win32k Type Isolation for SURFACE/Bitmap objects. Pixel-data buffers separated from SURFACE headers so adjacent-bitmap spray no longer reaches kernel pointers (Quarkslab).
Windows 10 1803 (April 2018 Update) Additional read/write primitives removed from the tagWND path.
Windows 10 1809 (October 2018 Update) Desktop-heap user/kernel separation for tagWND. The kernel tagWND is split into a kernel-only object plus a separately-allocated user-mode copy that contains no kernel addresses; only the user-mode copy is mapped into the application's address space.

5.2 The new layout: a kernel object with a +0x28 *pWND pointer

After the 1809 split, the kernel tagWND on x64 is roughly:

typedef struct _TAG_WND        /* names from the ByteWhite1x1 reverse-engineered header */
{
    HWND          hWnd;                /* 0x00  same as before                         */
    UINT64        windowCount;         /* 0x08                                         */
    Win32Thread*  pWin32Thread;        /* 0x10                                         */
    char          padding_1[0x10];     /* 0x18                                         */
    WindowStyle*  windowStyle;         /* 0x28  <-- "*pWND" pointer to user-mode copy  */
    UINT64        userCopyHeapOffset;  /* 0x30                                         */
    char          padding_2[0x20];
    _TAG_WND*     next;                /* 0x58                                         */
    _TAG_WND*     previous;            /* 0x60                                         */
    _TAG_WND*     parent;              /* 0x68                                         */
    _TAG_WND*     child;               /* 0x70                                         */
    char          padding_3[0x40];
    PWCH*         windowName;          /* 0xB8                                         */
    char          padding_4[0x8];
    _TAG_WND*     self;                /* 0xC8                                         */
} TAG_WND, *PTAG_WND;

Eoin Carroll (Trellix) explicitly labels the field at +0x28: “I've labeled it as *pWND because Microsoft no longer supplies symbols. … What is important to know about this pointer is that it's a user-mode version of the tagWND data that does not include kernel addresses, and it is structured differently than its parent tagWND structure.” The user-mode copy carries window-class properties propagated from WNDCLASSEX (style, window proc, background brush, menu refs, instance handle), but with user-mode addresses substituted for any kernel pointers.

5.3 Why this matters for ReactOS interpretation

If you read a modern Windows reverse-engineering article that says “at offset 0x28 of tagWND there is a pointer to pWND”, that statement is only true for Windows 10 1809 and later. In:

  • Windows 7 (and ReactOS): offset 0x28 (x64) / 0x14 (x86) is the start of the inline WW block — the field at that address is the state DWORD, not a pointer.
  • Windows 10 1809+: offset 0x28 is a pointer to the user-mapped “safe” copy of the WND data.

5.4 Why ReactOS does not implement Type Isolation for WND

A grep across the source confirms there is no tagWND_BASE, no WND_BASE, no Type Isolation infrastructure for window objects:

$ grep -rn "TypeIsolation\|tagWND_BASE\|WND_BASE" win32ss/ --include="*.h" --include="*.c"
(no relevant matches)

ReactOS targets binary compatibility with the Windows Server 2003 / Windows XP / Windows 7 era of win32k; the Type Isolation hardening was introduced years after that baseline. In ReactOS the “user copy” problem is solved instead by the desktop-heap double mapping (section 4.4): one allocation, two virtual addresses, with translation done at lookup time via ulClientDelta. There is no defence against the kernel-pointer leaks the Type Isolation work eliminated — that is a known gap of the ReactOS architecture.

7. End-to-end resolution of an HWND in ReactOS

HWND  ──► ValidateHwnd                       (user32: misc/misc.c:357)
            │
            ├─ fast path: hwnd == ClientInfo->CallbackWnd.hWnd
            │             return ClientInfo->CallbackWnd.pWnd       (already user-mapped)
            │
            └─ slow path: ValidateHandle(hwnd, TYPE_WINDOW)          (misc/misc.c:252)
                          │
                          ├─ pEntry      = GetUser32Handle(hwnd)
                          ├─ pEntry->ptr  ── kernel address of WND
                          └─ DesktopPtrToUser(pEntry->ptr)           (include/user_x.h:11)
                                            │
                                            └─ kernel_addr - ulClientDelta
                                              → user-side PWND

And from a kernel-side PWND, going back to the HWND is just UserHMGetHandle(pWnd) (i.e. pWnd->head.h), and the kernel self-pointer is pWnd->head.pSelf.
